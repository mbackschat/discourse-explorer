# Architecture map

One-liner per module + cross-cutting invariants. Start here when you need to figure out which file to open, or what gotchas apply across modules before making a change.

Module-specific deep dives are linked inline — follow the `→` pointer when your change is scoped to that module.

## Modules

- **`config.py`** — two-tier config + all Discourse-universal constants (`STRUCTURAL_TYPE_NAMES`, `STRUCTURAL_REL_PINS`, rate limits, `_OPENAI_EMBED_DIMS`, `_DEFAULT_ENTITY_TYPES`). `bootstrap(cli_data_dir)` is the single entry point. → [`vocabulary-and-config.md`](vocabulary-and-config.md)
- **`auth.py`** — `get_session(base_url, rc: RuntimeConfig)` auto-selects: API key → cookie → OIDC. Called only by `scraper`.
- **`scraper.py`** — HTTP + JSON writer. `run_sync(base_url, rc, full, dry_run)`. `RateLimitedClient` handles 1 s base delay, `Retry-After` on 429, 120 s cap, adaptive backoff. Enriches topic JSON with `category_name` + `plain_text`. Idempotent at the topic level — topic JSON is overwritten whole, not merged.
- **`discover_types.py`** — three-phase schema-discovery utility. Phase 1 profiles structural metadata (no LLM). Phase 2 samples N topics and asks the LLM what *kinds* of entities appear. Phase 3 distills into 4–6 content types. Writes directly to `<data-dir>/config/entity_types.json` (names + `structural` flag only — colors are the visualizer's concern). Persists audit artifact to `<data-dir>/discovery_result.json`. Imports `topic_to_document` from `query.py`. → [`vocabulary-and-config.md`](vocabulary-and-config.md) §Discovery
- **`query.py`** — LightRAG wrapper. `_get_rag(rc, ...)` builds the RAG (OpenAI or Ollama, auto-selected by `rc.is_openai`) with `FaissVectorDBStorage`. `addon_params["entity_types"]` receives only `content_type_names(vocab)` so Pass 2 can't *intentionally* produce structural types. `index_topics(rc, ...)` runs four passes (custom_kg seed → LLM extraction → structural enrichment via `aedit_entity` → entity-name canonicalization via `amerge_entities`). → [`multi-pass-indexing.md`](multi-pass-indexing.md)
- **`visualize.py`** — reads the graphml, emits browser-loaded `<data-dir>/visualize/{graph.html,data.js}` and build-time caches under `<data-dir>/visualize/cache/` (`layout.json`, `rel-clusters.json`). Owns all color decisions via `_PALETTE` + `_assign_colors(pinned_names, discovered_names)` — same palette for entity and rel types. Edge color matches the rel-bucket (not source node). All three of `data.js`, `graph.html`, and the rel-clusters cache have skip-if-identical write gates. **Invariant: the browser never loads anything from `cache/`**. Landing UX: defaults to Node View; Category view is one click away via the toolbar segmented toggle. The `entityType` mid-level view is still emitted but unreachable from the UI (kept for a future Tier-3 expand-in-place rework — see `docs/ideas/visualizer-feature-roadmap.md#9c`). `build_visualization` is a thin orchestrator over named seams (`_compute_node_metadata`, `_process_edges`, `_render_filter_section`, …) that future features should extend. → [`visualize-build.md`](visualize-build.md) (Python build) + [`visualize-frontend.md`](visualize-frontend.md) (JS runtime)
- **`rel_clusters.py`** — edge-keyword classifier. **No hardcoded relationship vocabulary.** Pinned layer (three Discourse-universal pins from `config.STRUCTURAL_REL_PINS`) + discovered layer (llm-cluster mode: embed → k-means → Ward merge → prune-and-split → LLM relabel; token-cluster mode: top-N tokens). `_prune_and_split` handles both tiny-bucket replacement and imbalance — **drains excluding the biggest bucket** (subtle: otherwise drained centroids inflate biggest and the subsequent split starts worse). Bucket sizes computed via `_classify_edge`-equivalent edge-voting, so the rebalance metric matches what the sidebar shows. → [`rel-clusters-algorithm.md`](rel-clusters-algorithm.md)
- **`stats.py`** — `_connect(data_dir)` builds an in-memory DuckDB with views over `topics/*.json` and `categories.json`. No persisted DB. → [`duckdb-views.md`](duckdb-views.md)

## Non-obvious invariants (cross-cutting)

Read these before editing anything — they name the ways recent code has silently broken when someone didn't know the invariant.

- **Entity-type vocabulary is a JSON file, not source.** `<data-dir>/config/entity_types.json` (schema v2) is the single source of truth for names + structural flags; colors are painted by `visualize._PALETTE` at render time. Legacy `color` fields in older files are silently ignored. Don't reintroduce per-type color constants as Python variables.
- **Structural types are load-bearing.** `_topic_to_custom_kg` emits nodes typed `category`/`topic`/`tag`/`user` (lowercase — matches LightRAG's Pass 2 auto-lowering so the Counter merge can vote). The JSON keeps PascalCase as canonical labels; `load_entity_types` validates those names are present with `structural: true`.
- **Pass 3 (`_enrich_structural_types`) is the contract that keeps Pass 1's typing alive.** LightRAG's Counter-vote merge tie-breaks in favor of the Pass 2 batch, silently retyping ~50% of categories otherwise. `aedit_entity` is a direct write that bypasses the vote. Don't remove Pass 3 without an equivalent guarantee.
- **Entity *names* are keyed by exact string** — case, whitespace, and prefix/suffix paraphrases all produce distinct nodes. Pass 3 fixes the type axis; **Pass 4** (`_canonicalize_case_dupes` + `_canonicalize_user_paraphrases` via `amerge_entities`) fixes the name axis by collapsing case-fold dupes and `^User ` / ` Person$` paraphrases of Pass-1 user seeds. Background + observed numbers: [`entity-name-canonicalization.md`](entity-name-canonicalization.md).
- **Per-run config lives in `<data-dir>/config/.env`, not `<project-root>/.env`.** The project-root file is a 1-line selector for `DISCOURSE_DATA_DIR`. Data-dir values win on collision (`load_dotenv(..., override=True)`).
- **`bootstrap(cli_data_dir)` is the single runtime-config entry point.** Every CLI calls it once after arg parsing; helpers receive the returned `RuntimeConfig`. Don't re-read `os.environ` ad-hoc inside code paths.
- **Switching embedding model or dimension requires `--clear`** — vectors are stored at a fixed dim in `graphrag/faiss_index_*.index`. Applies to provider switches, within-provider model swaps, and vector-backend swaps.
- **OpenAI embedding APIs cap input at 8192 tokens.** `_split_for_embedding` in `query.py` pre-chunks. LightRAG's normal `ainsert` chunks at 1200, so only the custom-KG chunks we author ourselves need the pre-split.
- **Entity types tight (constrained at LightRAG boundary); relation keywords loose (free-form at ingestion).** Types drive classification (UI, filter, group); keywords drive embedding-based retrieval in global-mode. Constraining keywords globally would degrade retrieval. Only structural edges get canonical keywords.
- **LightRAG caches LLM responses on disk inside `graphrag/`.** Deleting only the graphml leaves stale caches; always use `--clear` for a true rebuild.
- **`graphrag/` disk usage scales with corpus × embedding dim.** Faiss: ~120–200 MB for 1300 topics × 3072d. `-small` (1536d) roughly halves. (Previous NanoVectorDB was ~500 MB for the same — switch requires `--index --clear`.)
- **DuckDB category resolution is in the `topics` view** (subcategory → parent via `categories.json`). Downstream views inherit; don't re-resolve in ad-hoc queries.
- **`response_time` in `topic_threads` is a DuckDB `INTERVAL`.** Use `EXTRACT(EPOCH FROM response_time)` to get seconds.
- **`discover_types.py` imports `topic_to_document` from `query.py`.** Don't rename back to underscored — breaks the cross-module contract.
